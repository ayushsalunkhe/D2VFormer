## Executive Summary

**Current Status:** The project uses D2Vformer_simple trained for fixed 96h→96h forecasting. The model DOES use calendar timestamps internally via Date2Vec, but our current implementation does NOT demonstrate the paper's core flexible forecasting innovation.

**Root Cause:** The model architecture has a hard-coded dependency on `pred_len` in:
1. Line 66 of `D2Vformer_simple.py`: `D2V_y_date = D2V_output[:, -self.pred_len:, :]`
2. Fusion_Block output shape is always `(B, pred_len, D)`
3. Training and inference both assume fixed consecutive future windows

**Key Finding:** The original repository DOES contain a separate `Flexib_Prediction` module that implements the paper's intended flexible forecasting mechanism, but we have NOT used it in Semester 1.

**Solution Path:** We must either:
- **Option A (Faithful):** Use the official `Flexib_Prediction` module to train and evaluate flexible forecasting
- **Option B (Extension):** Modify D2Vformer_simple to accept variable-length future timestamp queries at inference

## Part 1: Current Architecture Analysis

### 1.1 How Historical Timestamps Are Represented

**File:** `D2Vformer_simple.py`, lines 51-58

```python
def forward(self, x_enc, x_mark_enc, x_dec, x_mark_dec, mode):
    # x_mark_enc: [B, seq_len, 27]  — historical calendar features
    # x_mark_dec: [B, label_len+pred_len, 27]  — future calendar features
    
    # Concatenate history + future timestamps
    D2V_input = torch.cat((x_mark_enc, x_mark_dec[:, -self.pred_len:, :]), dim=-2)
    
    # Select specific calendar features (hour, weekday, day, month)
    D2V_input = D2V_input[:, :, self.mark_index].transpose(-1,-2)  # (B, D_mark, L+O)
```

**Shape flow:**
- `x_mark_enc`: `(B, 96, 27)` — 27 calendar features for each of 96 historical hours
- `x_mark_dec[:, -96:, :]`: `(B, 96, 27)` — 27 calendar features for next 96 future hours
- After concat: `(B, 192, 27)` — total 192 timestamps (96 history + 96 future)
- After indexing: `(B, 192, 4)` — selected features (hour, weekday, day, month via mark_index=[0,1,2,3])
- After transpose: `(B, 4, 192)` — ready for Date2Vec

### 1.2 How Future Timestamps Are Represented

**Same process as above.** The future timestamps come from `x_mark_dec`, which is generated by the Dataset class:

**File:** `data/dataset.py` (D2Vformer module), line 36-38

```python
seq_y_mark = self.stamp[d_begin:d_end]  # stamp is the calendar feature array
# d_begin = e_end - label_len = 96 - 48 = 48
# d_end = e_end + pred_len = 96 + 96 = 192
# So seq_y_mark contains 144 timestamps (48 overlap + 96 future)
```

**Critical Constraint:** The dataset always generates **consecutive adjacent timestamps**. There's no mechanism to query arbitrary non-adjacent future dates like "2022-04-15, 2022-04-20, 2022-05-01".

### 1.3 Where Does Date2Vec Operate?

**File:** `layers/Date2Vec.py`, `Date2Vec_Fourier` class

**Input:** 
- `data`: `(B, D_feature, L)` — historical feature data
- `tau`: `(B, D_mark, L+O)` — concatenated history+future calendar features
- `mode`: 'train' or 'test'

**Process:**
1. Extracts frequency spectrum from historical data via FFT
2. Upsample low-frequency components using learnable linear layers
3. Compute phase and magnitude
4. Use Fourier series to encode calendar periodicity
5. Fuse with frequency information from data

**Output:** `(B, D_feature, L+O, k)` where k=T2V_outmodel (embedding dimension, e.g., 36)

**Key Observation:** Date2Vec processes the ENTIRE concatenated timestamp sequence (L+O) in one pass. It doesn't inherently require consecutive timestamps — it operates on whatever tau you provide.

### 1.4 How Does Fusion Block Consume Future Timestamps?

**File:** `layers/Fusion_Block.py`, `Fusion_Block_s` class

**Input:**
- `x`: `(B, L, D)` — historical features
- `x_date`: `(B, L, D, k)` — Date2Vec embeddings for history
- `y_date`: `(B, O, D, k)` — Date2Vec embeddings for future
- `mode`: 'train' or 'test'

**Process (lines 155-168):**
```python
# 1. Project future date embeddings
fc = self.fc_out(y_date)  # (B, O, D, k) → (B, O, D, d_model)

# 2. Attention: match future dates against historical features+dates
Q = fc  # Query: future date embeddings
K = torch.cat([x.unsqueeze(-1), x_date], dim=-1)  # Key: history features + date embeddings
K = self.fc_k(K)  # Project to d_model

# 3. Compute attention scores
scores = torch.einsum("bqdm,bldm->bqdl", Q, K) / sqrt(d_model)
A = softmax(scores, dim=-1)  # (B, D, O, L) — attention weights

# 4. Weighted sum over history
V = torch.einsum("bld,bdlp->bdp", x, A)  # (B, D, O)
```

**Output:** `(B, O, D)` — predictions for O future timestamps

**Key Finding:** The Fusion Block's attention mechanism is INHERENTLY FLEXIBLE. It computes attention between:
- Query: each future timestamp embedding
- Key/Value: all historical timestep features

There's NO architectural constraint requiring O (pred_len) to be fixed. The attention can work with any number of future queries.

### 1.5 Is the Current Architecture Intrinsically Capable of Variable Prediction Length?

**Answer: YES and NO**

**YES — The Core Mechanism:**
- Date2Vec can encode any set of timestamps (consecutive or non-adjacent)
- Fusion Block attention can match any number of future queries against history
- There's no inherent limitation in the attention computation

**NO — The Current Implementation:**

**Hard-coded dependency #1:** Line 57, `D2Vformer_simple.py`
```python
D2V_input = torch.cat((x_mark_enc, x_mark_dec[:, -self.pred_len:, :]), dim=-2)
```
This SLICES the future timestamps to exactly `pred_len`. If you trained with pred_len=96, this line will always extract 96 future timestamps from x_mark_dec.

**Hard-coded dependency #2:** Line 66, `D2Vformer_simple.py`
```python
D2V_y_date = D2V_output[:, -self.pred_len:, :, :]
```
This SLICES Date2Vec output to extract exactly `pred_len` future embeddings.

**Hard-coded dependency #3:** Dataset generation
The `MyDataset` class in `data/dataset.py` always generates windows with fixed `label_len + pred_len` future timestamps. There's no variable-length sampling.

### 1.6 Which Tensors Depend on pred_len?

**At Training Time:**
1. `x_mark_dec` shape: `(B, label_len + pred_len, 27)` — hard-coded in dataset
2. `D2V_y_date` shape: `(B, pred_len, D, k)` — sliced in forward pass
3. `prediction` output shape: `(B, pred_len, D)` — determined by D2V_y_date length
4. Loss computation: `criterion(pred, target[:, -pred_len:, :])` — expects fixed pred_len

**At Inference Time:**
Same as training. The model checkpoint contains no pred_len-dependent parameters (like the buggy full D2Vformer's linear_out layer), but the forward pass logic hard-codes pred_len.

### 1.7 Is the Dependency Architectural or Implementation-Only?

**Answer: IMPLEMENTATION-ONLY**

The Fusion Block and Date2Vec have NO learnable parameters that depend on pred_len. The dependency is purely in:
- How we slice tensors (lines 57, 66)
- How the dataset generates samples

**This is GOOD NEWS:** We can make the model flexible without retraining, IF we modify the forward pass and data loading correctly.

### 1.8 Can One Trained Model Accept Different Future Timestamp Sets at Inference?

**Theoretical Answer: YES**

If we modify the forward pass to:
1. Accept variable-length `x_mark_dec`
2. Remove the `[:, -self.pred_len:]` slicing
3. Let Date2Vec and Fusion Block process whatever future timestamps are provided

Then a model trained on pred_len=96 could theoretically predict for 48h, 72h, 96h, 192h without retraining.

**Practical Caveats:**
1. **Extrapolation risk:** The model was trained to see exactly 96 consecutive future timestamps. Asking it to predict 192h means it's never seen attention patterns over 192 future positions during training.
2. **Label_len mismatch:** If we change pred_len at inference, do we also change label_len? The original design uses label_len for decoder input in transformer-style models.
3. **Performance degradation:** Even if it "works," accuracy will likely degrade for horizons far from the training distribution.

### 1.9 Can It Handle Non-Adjacent Future Timestamps?

**Architectural Capability: YES**

The attention mechanism in Fusion Block computes:
```
attention(future_query_i, all_history) → prediction_i
```

Each future query is processed independently. There's NO assumption that queries are consecutive.

**Current Implementation: NO**

The dataset always generates consecutive timestamps. We have no code path to create samples like:
```
History: 2022-04-01 00:00 ... 2022-04-05 00:00
Future queries: [2022-04-07 12:00, 2022-04-12 09:00, 2022-04-20 18:00]
```

**Required Changes:**
1. New dataset class that accepts arbitrary future timestamps
2. Modified forward pass that doesn't assume consecutive slicing
3. Evaluation logic that compares predictions against non-adjacent ground truth

**The Paper's Flexible Prediction Mechanism:**

The repository includes a SEPARATE module `Flexib_Prediction/` that implements:

2. **Testing:** Evaluate the SAME trained model on multiple horizons (48h, 72h, 96h, 108h) WITHOUT retraining

**Key Files:**

- `Flexib_Prediction/data/dataset.py` — `flexible_D2V_Dataset` class
- `Flexib_Prediction/main.py` — entry point with `--exp flexiable_prediction` flag

**Implementation Strategy:**

Looking at `exp_flexiable.py` lines 140-162:
```python

                                     label_len=self.label_len, pred_len=self.pred_len)
```

But examining `flexible_D2V_Dataset` (lines 105-128 in `data/dataset.py`), it's actually IDENTICAL to the standard `MyDataset` — single pred_len only!

**Confusion Alert:** The naming is misleading. The "flexible" dataset isn't actually flexible in the sense of variable-length queries within one sample.

**The REAL Flexible Mechanism:**

Looking more carefully at the test loop (exp_flexiable.py lines 377-402), the flexibility comes from:

1. Train one model with pred_len=96
2. At test time, create SEPARATE test dataloaders with pred_len=48, 72, 96, 108
3. Run inference on each test set
4. Compare results

**This is "flexible" in the sense that ONE trained checkpoint can be evaluated on DIFFERENT fixed horizons, but NOT in the sense of arbitrary timestamp queries within a single forward pass.**

### 1.11 Is There Other Flexible Prediction Code?

**Found:** `Flexib_Prediction/data/dataset_skip.py`

This contains `MyDataset_stride` which has a `stride` parameter:
```python
class MyDataset_stride(Dataset):
    def __init__(self, data, seq_len=96, label_len=48, pred_len=96, stride=0):
        self.stride = stride
    
    def __getitem__(self, index):
        e_end = e_begin + self.seq_len
        s = e_end + self.stride  # INSERT A GAP between history and future
        d_begin = s - self.label_len
        d_end = s + self.pred_len
```

**This implements NON-ADJACENT forecasting!**

With `stride=24`, you get:
- History: hours 0-95
- Gap: hours 96-119 (24 hours)
- Prediction: hours 120-215

This is closer to arbitrary-position forecasting, but still uses consecutive prediction windows (just shifted by a gap).

### 1.13 Does the Paper's Arbitrary-Position Forecasting Require Different Architecture?

**Answer: NO, but YES for the inference API**

**Architecture:** D2Vformer_simple is sufficient. The Fusion Block's attention mechanism is inherently flexible.

**Inference API:** We need to:
1. Remove hard-coded `pred_len` slicing
2. Accept variable-length future timestamp inputs
3. Let the model output variable-length predictions

**The paper's "flexible" claim refers to TWO capabilities:**

**Capability 1 (Easy):** Variable fixed horizons
- Train once on 96h→96h
- Test on 48h, 72h, 96h, 192h by creating separate test sets
- This is what `Flexib_Prediction` implements

**Capability 2 (Hard):** Arbitrary timestamp queries
- Query specific future dates: "What will PM2.5 be on April 15, April 20, May 1?"
- This requires non-consecutive timestamp handling
- The paper DOES NOT provide code for this
- Would require significant modification

## Part 2: Root Cause Analysis

### 2.1 Why Our 96h Checkpoint Cannot Be Used for 192h

**Immediate Cause:** Shape mismatch at line 57

When we try to load a 96h checkpoint and run inference with pred_len=192:

```python
# Dataset generates x_mark_dec with shape (B, 48+192, 27) for label_len=48, pred_len=192
# Forward pass tries to slice:
D2V_input = torch.cat((x_mark_enc, x_mark_dec[:, -96:, :]), dim=-2)  # ← WRONG! Tries to take last 96 from 240

# This "works" but gives wrong timestamps:
# x_mark_dec[:, -96:, :] extracts hours 144-240 instead of hours 48-240
# Date2Vec gets the wrong future timestamp range
# Fusion Block predicts for wrong time positions
```

**Deeper Issue:** Even if we fix the slicing, the model outputs will be wrong length:

```python
# After Date2Vec with corrected slicing, we'd have:
D2V_output shape: (B, D, 96+192, k)  # 96 history + 192 future

# Line 66 slices:
D2V_y_date = D2V_output[:, -96:, :, :]  # ← Takes last 96 instead of last 192!

# Fusion Block receives only 96 future queries, outputs (B, 96, D)
# But ground truth is (B, 192, D) — shape mismatch in loss calculation
```

**Fundamental Issue:** The forward pass assumes `pred_len` is a static constant, not a dynamic input parameter.

### 2.2 Why This Matters for the Main Innovation

**The paper's value proposition:**

> "Unlike traditional models that require retraining for different horizons, D2Vformer uses Date2Vec to encode actual calendar timestamps, enabling flexible forecasting at arbitrary future positions."

**What we showed in Semester 1:**

> "We trained D2Vformer and DLinear on 96h→96h. DLinear wins."

**What's missing:**

> "We did NOT show that D2Vformer can predict 48h, 96h, 192h, 336h with ONE trained model, while DLinear needs FOUR separate models."

This is the key differentiator. Without demonstrating variable-horizon capability, we're not showcasing D2Vformer's core innovation.

### Option B: Modify D2Vformer_simple for Dynamic pred_len (More Complex)

**Why Consider This:**
- More control over the implementation
- Can add true arbitrary timestamp queries (non-consecutive)
- Educational value in understanding the mechanism

**Required Changes:**

#### Change 1: Make pred_len a Forward Pass Parameter

**File:** `model/D2Vformer_simple.py`

**Current:**
```python
def __init__(self, configs):
    self.pred_len = configs.pred_len  # Fixed at initialization

def forward(self, x_enc, x_mark_enc, x_dec, x_mark_dec, mode):
    D2V_input = torch.cat((x_mark_enc, x_mark_dec[:, -self.pred_len:, :]), dim=-2)
    D2V_y_date = D2V_output[:, -self.pred_len:, :, :]
```

**Modified:**
```python
def __init__(self, configs):
    self.default_pred_len = configs.pred_len  # Store default, but don't enforce

def forward(self, x_enc, x_mark_enc, x_dec, x_mark_dec, mode, pred_len=None):
    # Use dynamic pred_len if provided, else default
    if pred_len is None:
        pred_len = self.default_pred_len
    
    # Dynamically slice based on provided pred_len
    D2V_input = torch.cat((x_mark_enc, x_mark_dec[:, -pred_len:, :]), dim=-2)
    
    D2V_output = self.Date2Vec(x_enc.permute(0,2,1), D2V_input, mode)
    D2V_output = D2V_output.permute(0, 2, 1, 3)
    
    D2V_x_date = D2V_output[:, :self.seq_len, :, :]
    D2V_y_date = D2V_output[:, -pred_len:, :, :]  # Dynamic slicing
    
    prediction_var = self.fusion(x_enc, D2V_x_date, D2V_y_date, mode)
    
    return prediction_var  # Shape: (B, pred_len, D)
```

#### Change 2: Flexible Dataset Class

**File:** `data/dataset.py`

```python
class FlexibleDataset(Dataset):
    """Dataset that can generate samples with different pred_lens on the fly."""
    def __init__(self, data, stamp, seq_len=96, label_len=48, pred_lens=[48, 72, 96, 192]):
        self.data = data
        self.stamp = stamp
        self.seq_len = seq_len
        self.label_len = label_len
        self.pred_lens = pred_lens  # List of possible prediction lengths
        self.max_pred_len = max(pred_lens)
    
    def __getitem__(self, index):
        e_begin = index
        e_end = e_begin + self.seq_len
        
        # Always generate up to max_pred_len
        d_begin = e_end - self.label_len
        d_end = e_end + self.max_pred_len
        
        seq_x = self.data[e_begin:e_end]
        seq_y = self.data[d_begin:d_end]
        seq_x_mark = self.stamp[e_begin:e_end]
        seq_y_mark = self.stamp[d_begin:d_end]
        
        return seq_x, seq_y, seq_x_mark, seq_y_mark
    
    def __len__(self):
        return len(self.data) - self.seq_len - self.max_pred_len + 1
```

#### Change 3: Flexible Inference Function

```python
def flexible_inference(model, testloader, pred_lens=[48, 72, 96, 192]):
    """Run inference with multiple prediction horizons using the same model."""
    results = {}
    
    for pred_len in pred_lens:
        preds, trues = [], []
        
        for (batch_x, batch_y, batch_x_mark, batch_y_mark) in testloader:
            # Forward pass with dynamic pred_len
            with torch.no_grad():
                pred = model(batch_x, batch_x_mark, batch_y, batch_y_mark, 
                            mode='test', pred_len=pred_len)
            
            # Extract the relevant portion of ground truth
            preds.append(pred.cpu().numpy())
            trues.append(batch_y.cpu().numpy()[:, -pred_len:, :])
        
        preds = np.concatenate(preds)
        trues = np.concatenate(trues)
        
        mse = np.mean((preds - trues) ** 2)
        mae = np.mean(np.abs(preds - trues))
        
        results[pred_len] = {'mse': mse, 'mae': mae}
    
    return results
```

## Part 8: Expected Results & Limitations

### What We Expect to See

**Scenario 1: D2Vformer Generalizes Well**

If Date2Vec's calendar embeddings truly help:
- MSE at 48h: Better than 96h (shorter horizon easier)
- MSE at 96h: 0.6982 (training distribution)
- MSE at 192h: Slightly worse than 96h (extrapolation)
- MSE at 336h: Worse, but still reasonable

**Scenario 2: D2Vformer Struggles with Extrapolation**

If the model overfits to 96h patterns:
- MSE at 48h: Worse than 96h (model trained to look 96 steps ahead)
- MSE at 96h: 0.6982 (training distribution)
- MSE at 192h: Much worse (never seen this horizon)
- MSE at 336h: Terrible (complete extrapolation failure)

**Scenario 3: DLinear Always Wins**

If linear models are fundamentally better for this data:
- DLinear beats D2Vformer at ALL horizons
- But DLinear needed 4× retraining
- Story: "DLinear is more accurate, but D2Vformer is more flexible"

### Known Limitations

**Limitation 1: Training Distribution Mismatch**

The model was trained to predict CONSECUTIVE 96 future steps. When we ask it to predict 192 steps, it's operating outside the training distribution. Accuracy may suffer.

**Mitigation:** Train explicitly on multiple horizons (mix 48h, 96h, 192h samples in training).

**Limitation 2: Not True Arbitrary Timestamps**

Even with flexible horizons, we're still predicting CONSECUTIVE windows (just of variable length). We're NOT querying specific non-adjacent dates like "April 7, April 15, May 1".

**Mitigation:** Implement Option B (arbitrary timestamp queries) as Semester 2 extension.

**Limitation 3: Delhi AQI High Volatility**

Our Delhi AQI results already show both models struggle with high-frequency spikes. Flexible forecasting may not improve this — the issue is missing external variables (traffic, weather).

**Mitigation:** Document this honestly as a domain-specific challenge, separate from the flexibility mechanism.
